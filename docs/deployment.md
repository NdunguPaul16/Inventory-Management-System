# Deployment preparation

These files prepare separate deployments. No service is deployed by this repository change.

## Render backend

Create a Render Blueprint from the `dfstock` branch using `render.yaml`. Keep the service root at the repository root so the build can install and compile `shared/` before `backend/`. The Blueprint pins the service to `dfstock` and disables automatic deployments. Its install command includes development dependencies needed for the TypeScript build, then it builds the backend workspace and starts its existing `dist/index.js` entry point through `npm run start -w backend`.

Supply `MONGODB_URI` for a replica-set MongoDB, unique `AUTH_ACCESS_TOKEN_SECRET` and `AUTH_REFRESH_TOKEN_SECRET` values of at least 32 characters, and `CORS_ORIGINS` with the Vercel frontend origin. The Blueprint requests these values at creation time; do not commit them. The existing `/api/v1/health` endpoint is the service health check. First-admin provisioning is an explicit CLI operation, not a server-startup action: from the repository root, build with `npm run build:shared && npm run build -w backend`, then run `npm run bootstrap:admin -w backend` in an interactive Render Shell. Render Shell is available for paid web services, not Free web services. The repository's `render.yaml` does not specify the deployed plan, so confirm Shell access in the Render dashboard.

If an interactive Render Shell is unavailable, Render documents one-off jobs that use the base service's latest build and a snapshot of its environment. Use a staging service that points at the staging database; do not attach this job to a production service for a staging bootstrap. For a one-off job, provide `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_EMAIL`, and `BOOTSTRAP_ADMIN_PASSWORD` as temporary protected environment values on that staging service, then set the job command to `npm run bootstrap:admin -w backend`. The running web process ignores these values; only the explicit CLI command provisions an account. Remove the temporary values after the job. Render plan and one-off job availability must be confirmed in the dashboard. If there is no suitable staging service or job option, run the same CLI locally with a private root `.env` containing `MONGODB_URI` for the intended staging cluster and `MONGODB_DB_NAME=ims`; `.env` is gitignored. The CLI requires a persistent MongoDB URI and will not use the development in-memory database.

## Vercel frontend

Create a Vercel project from the same repository, select `dfstock` as its Production Branch, set its Root Directory to `frontend/`, and enable **Include source files outside of the Root Directory in the Build Step** so `shared/` and the root lockfile are available. `frontend/vercel.json` installs the root npm workspaces including build dependencies, builds `shared/` and the frontend, and publishes `frontend/dist/`.

The first rewrite in `frontend/vercel.json` proxies `/api/*` to the Render backend while preserving the browser's same-origin API path and refresh cookie. The second rewrite serves `index.html` for frontend routes such as `/login` and `/dashboard`. No `RENDER_API_ORIGIN` environment variable is needed: Vercel validates its static `vercel.json` during project setup, before deployment environment variables are available. If the Render origin changes, update the API rewrite destination and redeploy. The existing local Vite proxy still targets `http://localhost:4000` by default.

After both services are configured, check `/api/v1/health` through the Vercel URL, then check login, refresh and a direct visit to a frontend route. Production authentication requires the same browser origin for the proxied API path. Provider builds and deployed behavior remain unverified until an actual Vercel and Render setup is reviewed.
