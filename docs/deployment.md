# Deployment preparation

These files prepare separate deployments. No service is deployed by this repository change.

## Render backend

On `staging/security-audit`, `render.yaml` describes only the staging backend and pins it to this branch with automatic deployments off. The production `dfstock` branch and its Render service are separate. Keep the staging service root at the repository root so the build can install and compile `shared/` before `backend/`. Its build includes development dependencies needed for TypeScript and uses the temporary `dist-staging/staging/index.js` entry point through `npm run start:staging -w backend`. The normal backend build emits `dist/index.js` without the staging diagnostic. Do not sync this staging Blueprint into the production service.

Supply `MONGODB_URI` for a replica-set MongoDB, unique `AUTH_ACCESS_TOKEN_SECRET` and `AUTH_REFRESH_TOKEN_SECRET` values of at least 32 characters, and `CORS_ORIGINS` with the Vercel frontend origin. The Blueprint requests these values at creation time; do not commit them. Create a same-region Render Key Value instance separately and set `AUTH_RATE_LIMIT_REDIS_URL` to its private internal URL as a protected Render environment value. Production startup now requires this store. The default login limits are 10 per IP per minute, 60 per IP per hour, and 5 per account per 15 minutes; the optional `AUTH_LOGIN_LIMIT_PER_IP_MINUTE`, `AUTH_LOGIN_LIMIT_PER_IP_HOUR`, and `AUTH_LOGIN_LIMIT_PER_ACCOUNT_15_MIN` variables override them. Leave `AUTH_TRUSTED_PROXY_CIDRS` unset until a staging proxy-chain test confirms the exact trusted ranges; an empty value uses the direct peer address and may group Vercel users under one IP budget. See [the rate-limit review](auth-rate-limit-review.md) for this release gate. The existing `/api/v1/health` endpoint is the service health check and now reports the authentication limiter's availability. First-admin provisioning is an explicit CLI operation, not a server-startup action: from the repository root, build with `npm run build:shared && npm run build -w backend`, then run `npm run bootstrap:admin -w backend` in an interactive Render Shell. Render Shell is available for paid web services, not Free web services. The repository's `render.yaml` does not specify the deployed plan, so confirm Shell access in the Render dashboard.

If an interactive Render Shell is unavailable, Render documents one-off jobs that use the base service's latest build and a snapshot of its environment. Use a staging service that points at the staging database; do not attach this job to a production service for a staging bootstrap. For a one-off job, provide `BOOTSTRAP_ADMIN_NAME`, `BOOTSTRAP_ADMIN_EMAIL`, and `BOOTSTRAP_ADMIN_PASSWORD` as temporary protected environment values on that staging service, then set the job command to `npm run bootstrap:admin -w backend`. The running web process ignores these values; only the explicit CLI command provisions an account. Remove the temporary values after the job. Render plan and one-off job availability must be confirmed in the dashboard. If there is no suitable staging service or job option, run the same CLI locally from `staging/security-audit` with a private root `.env` containing `MONGODB_URI` for the separate staging cluster, `MONGODB_DB_NAME=ims_staging`, and the staging and production host pins listed in [the staging setup](staging-security-audit.md). The staging branch's bootstrap command and CLI both check isolation before collecting credentials or connecting; a production `ims` target is rejected. `.env` is gitignored. The CLI requires a persistent MongoDB URI and will not use the development in-memory database. Do not use the staging bootstrap command from the production Render service or production checkout.

## Vercel frontend

Create a Vercel project from the same repository, select `dfstock` as its Production Branch, set its Root Directory to `frontend/`, and enable **Include source files outside of the Root Directory in the Build Step** so `shared/` and the root lockfile are available. `frontend/vercel.json` installs the root npm workspaces including build dependencies, builds `shared/` and the frontend, and publishes `frontend/dist/`.

On `staging/security-audit`, the first rewrite in `frontend/vercel.json` proxies `/api/*` only to `https://inventory-inc-staging-backend.onrender.com`, preserving the browser's same-origin API path and refresh cookie. The second rewrite serves `index.html` for frontend routes such as `/login` and `/dashboard`. Automatic Preview deployment remains disabled for this branch; create a protected Preview manually only after review, using the exact staging commit. No `RENDER_API_ORIGIN` environment variable is needed: Vercel validates its static `vercel.json` during project setup, before deployment environment variables are available. The existing local Vite proxy still targets `http://localhost:4000` by default. See [the staging setup](staging-security-audit.md) for protection, CORS, and manual Preview checks.

After both services are configured, check `/api/v1/health` through the Vercel URL, then check login, refresh and a direct visit to a frontend route. Production authentication requires the same browser origin for the proxied API path. Provider builds and deployed behavior remain unverified until an actual Vercel and Render setup is reviewed.
